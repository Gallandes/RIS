# Модель угроз района

**Район:** 8 — Городской SOC · **Команда:** 8 · **Версия:** v0 · **Дата:** 19.10.2026 · **Авторы:** Пашкеев Данил, Ефимцев Борис, Стовбун Ярослав, Ткаченко Тимур

## 1. Политика безопасности района
Записывать журналы в SOC могут только сервисы районов, и каждый — только от имени своего района; принятые журналы никто, включая администратора SOC, не изменяет и не удаляет — только дозапись. Читать журналы и инциденты может только аналитик SOC; менять правила обнаружения и настройки SIEM — только администратор SOC, и каждое изменение записывается в журнал. Район, от которого нет журналов дольше 5 минут, — «слепая зона», по нему открывается инцидент.

## 2. Активы — что защищаем
| Актив | Где хранится / проходит | Что важнее | Почему ценен |
|---|---|---|---|
| Журналы районов | поток П1 → collector → siem, archive | целостность, доступность | флаг «целостность журналов»; без них нельзя ответить «кто и как атаковал» (атрибуция) |
| Неизменяемая копия журналов | archive | целостность | доказательство при споре на Purple-разборе, если основной индекс подменён |
| Правила обнаружения и корреляции | siem, репозиторий SOC | целостность | отключённое правило = флаг «необнаруженная атака» |
| Алерты и инциденты | siem → api → db, событие `soc.incident.opened` | целостность, доступность | по ним районы реагируют; ложный инцидент отвлекает, удалённый — скрывает атаку |
| Статус источников (кто шлёт журналы) | db | целостность | по нему видны слепые зоны |
| Учётные записи аналитиков и администратора SOC | dashboards, db, (с нед. 4) Паспортный стол | конфиденциальность, целостность | админ SOC может всё: удалить индекс, выключить правила |
| Пароль базы и учётки SIEM | `.env` на хосте района | конфиденциальность | дают доступ к данным в обход api и журналов |
| Секреты и токены CI | ci-раннер | конфиденциальность | через CI можно попасть в репозитории всех районов |
| Сведения в журналах (IP, логины, request_id) | siem, dashboards | конфиденциальность | карта города для атакующего: кто, где, какие сервисы |
| Доступность приёма журналов | collector | доступность | пока collector лежит, атаки не видны |

## 2а. Что есть у атакующего (активы атакующего)
| Возможность атакующего | Откуда она у него | Куда может привести |
|---|---|---|
| Право отправлять журналы в collector | есть у сервиса любого района | поддельные записи от имени чужого района, флуд, инъекция в поля журнала |
| Право публиковать события в Транспорт | есть у любого района | поддельный `grid.alarm.raised` / `block.added` → ложные инциденты |
| Захваченный сервис или хост другого района | результат успешной атаки в раунде | остановить отправку журналов, чистить их до отправки |
| Открытый код и документация SOC (white-box) | режим white-box | знает формат журналов, правила корреляции, пороги алертов — и как их обойти |
| Учётная запись рядового сотрудника / аналитика | инсайдерская карта (раунд 3), фишинг | чтение журналов всего города, тихое закрытие инцидентов |
| Возможность прислать код в CI (merge request, зависимость) | любой разработчик района | выполнение кода на ci-раннере, кража токенов |

## 3. Участники и роли
| Роль / принципал | Что может делать | Как аутентифицируется |
|---|---|---|
| Сервис района (источник журналов) | отправлять журналы только своего района | пока никак → mTLS-сертификат городского УЦ (нед. 3–4) |
| Аналитик SOC | искать по журналам, смотреть дашборды, открывать и вести инциденты | пока локальная учётка → SSO Паспортного стола, роль `soc-analyst` (нед. 4) |
| Старший аналитик / дежурный | закрывать инциденты, помечать ложные срабатывания | SSO, роль `soc-lead` (нед. 4) |
| Администратор SOC | управлять контейнерами, SIEM, правилами, ретеншном | SSH-ключ на хост, `.env`; учётка admin в SIEM |
| Транспорт (сервис) | доставлять события `grid.alarm.raised`, `block.added`, `delivery.failed`; забирать `soc.incident.opened` | пока никак → mTLS (нед. 3–4), подпись событий (нед. 5) |
| Шлюз (сервис) | отправлять журналы и `block.added` | mTLS (нед. 3–4) |
| Разработчик района | запускать проверки CI на своём репозитории, видеть свои результаты | пока никак → SSO / токен репозитория |
| White Team (чекер) | `GET /health` | не нужно |

## 5. Границы доверия
| Граница | Что по разные стороны | Как контролируется |
|---|---|---|
| Г1 город / SOC | все районы, Шлюз, Red Team → collector, api, ids | пока никак → TLS (3), mTLS отправителей (3–4), SSO аналитиков (4), сегментация (6) |
| Г2 сервисы / данные | collector, api, dashboards → siem, db, archive | пароль из `.env`, порты не опубликованы → раздельные учётки, archive только на дозапись (7) |
| Г3 район / шина | события любых районов ↔ api | пока никак → подпись, проверка `source`, отбрасывание повторов по `id` (5) |
| Г4 админ / сервисы | человек с SSH → всё | SSH-ключ, журнала действий админа нет → журнал в archive (7) |
| Г5 код районов / CI | чужой код → раннер с секретами | пока никак → изолированный раннер без секретов (7) |

## 6. Модель нарушителя
| Противник | Возможности | Мотив | Вероятность для нас |
|---|---|---|---|
| Н1. Red Team / атакующий из сети города | сетевой доступ к collector и api через Шлюз; white-box (знает формат журналов и правила); сканеры, публичные эксплойты | атаковать районы и не попасть в журналы; в игре — флаг «необнаруженная атака» | высокая |
| Н2. Атакующий, захвативший другой район | права на хосте района и его сервисе-отправителе журналов; право публиковать события в Транспорт | замести следы: остановить отправку, вычистить журналы, отправить подделку от имени района | высокая |
| Н3. «Шумовик» | генерирует трафик и события, имеет право слать журналы и события | утопить реальную атаку в ложных срабатываниях, перегрузить collector и siem (alert fatigue, DoS) | средняя |
| Н4. Инсайдер — аналитик или администратор SOC (внутренний) | роль `soc-analyst` / admin, SSH, `.env`, доступ к правилам и индексам | ошибка или умысел (в раунде 3 — инсайдерская карта): отключить правило, закрыть инцидент, удалить индекс | средняя |
| Н5. Атакующий цепочку поставок CI (внутренний для города) | merge request в репозиторий района, подмена зависимости или образа | выполнить код на ci-раннере, украсть токены, отключить сканеры | низкая |

## 8. Дерево атаки (для самой ценной цели)
Самая ценная цель атакующего для SOC — флаг «необнаруженная атака».

```
Цель: атака на район X прошла, а в SOC нет ни алерта, ни инцидента
├── ИЛИ: журналы атаки не дошли до SOC
│   ├── ИЛИ: остановить отправку журналов на захваченном хосте района X        (T02, слепая зона)
│   ├── ИЛИ: вычистить свои строки до отправки                                  (T02)
│   │   └── И: права root на хосте X + знание формата Р4 (открыт: white-box)
│   └── ИЛИ: положить collector флудом                                          (T05)
│       └── И: право слать журналы + нет лимитов на источник
├── ИЛИ: журналы дошли, но правило не сработало
│   ├── ИЛИ: обойти сигнатуру (white-box: правила SOC открыты)
│   ├── ИЛИ: атаковать мимо IDS (TLS, незеркалируемый сегмент)                  (T13)
│   └── ИЛИ: отключить правило
│       ├── ИЛИ: инсайдер / украденная учётка админа SIEM                       (T07, T09)
│       └── ИЛИ: войти в открытые dashboards без пароля                         (T10)
├── ИЛИ: алерт был, но потерялся
│   ├── ИЛИ: утопить в ложных срабатываниях                                     (T04, T12, Н3)
│   │   └── И: доступ к шине или API + атака в тот же момент
│   └── ИЛИ: закрыть инцидент как «ложный»                                     (T09, T14)
└── ИЛИ: следы удалены после обнаружения
    └── И: доступ к siem с правом удаления + нет неизменяемой копии в archive   (T07, T08)
```

**Общие участки дерева.** Мера M2 «контроль слепых зон» (алерт, если источник замолчал) закрывает сразу две ветки «журналы не дошли» — остановку отправки и падение collector. Мера M7 (неизменяемый archive) закрывает весь путь «следы удалены». Мера M8 (журнал действий админа с `actor`) — ветки «отключить правило» и «закрыть инцидент». Это лучшие места для защиты.

## 9. Меры защиты
Меры для угроз с риском ≥ 12 и пяти самых опасных (T02, T01, T05, T07, T06).

| Мера | Угрозы | Что делаем | Кто отвечает | Когда |
|---|---|---|---|---|
| M1 | T01 | Отправитель журналов аутентифицируется mTLS-сертификатом УЦ; collector сверяет `district` в записи с CN сертификата и отбрасывает несовпадения с записью `log.rejected` | инж. инфраструктуры | нед. 3–4 |

| M4 | T04 | Принимать `grid.alarm.raised` только с проверенной подписью и `source` = `/d6-grid/…`; отбрасывать повторы по `id` | тимлид + Транспорт | нед. 5 |
| M5 | T05 | Лимит частоты и размера на источник в collector, буфер на диске, отдельная очередь на каждый район; алерт при переполнении | инж. инфраструктуры | нед. 7 |

| M11 | T12, T14 | API и dashboards — только с токеном SSO; роли `soc-analyst` / `soc-lead` / `soc-admin`, проверка роли на каждой операции | разработчик-аналитик | нед. 4 |
| M12 | T13 | Зеркало трафика Шлюза на Suricata; журналы TLS-прокси Шлюза (SNI, JA3) в SOC вместо расшифровки | инж. инфраструктуры + Шлюз | нед. 6–7 |
| M16 | T18, T19 | Обязательные шаги CI задаёт SOC (шаблон, который район не может отключить); раннер для чужого кода без секретов; gitleaks на каждом коммите | инж. безопасности | нед. 7 |

Меры для угроз с риском < 12 (план на v1): M3 — строгий JSON-парсер, экранирование управляющих символов; M10 — TLS на П1 (нед. 3); M13 — Trivy для образов SOC, обновление образов; M14 — Транспорт хранит недоставленные события, SOC сверяет `delivery.failed`; M15 — пароль только в `.env`, проверка `pack.sh` (сделано).

## 10. Остаточные риски
- **T02 полностью не закрываем.** Если атакующий получил root на хосте района, он может слать «чистые» журналы, и SOC это не докажет. Снижаем через M2 (сравнение с журналами Шлюза), но 100 % гарантии нет — это граница ответственности района-источника.
- **T13 частично.** Расшифровывать TLS-трафик районов мы не будем (дорого и нарушает приватность); видим только метаданные.
- **T16** — доступность Транспорта вне нашего района; принимаем риск, сверяем `delivery.failed`.
- **Ложные срабатывания** — устранить нельзя, только снижать порогами и разбором на Purple-сессиях.

## 11. Использование LLM
Черновик модели угроз подготовлен с помощью LLM, затем проверен командой по своей DFD; запись — в `docs/llm-log.md`. Сравнение моделей на STRIDE — каталог `l1/`.
