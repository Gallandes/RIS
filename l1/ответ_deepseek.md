# Черновик модели угроз по STRIDE

## Сервис: Центр мониторинга (collector + api + OpenSearch Dashboards)

> **Оговорка:** архитектура Шлюза (какие протоколы терминируются, есть ли WAF)
> и политика на шине (схемы, аутентификация издателей) в описании не
> детализированы. Соответствующие меры ниже — базовые рекомендации, а не
> утверждение о текущем состоянии.

---

## 1. Элементы схемы потоков данных (DFD)

Для модели выбрано 8 элементов, чтобы покрыть ключевые границы доверия,
не раздувая таблицу.

1. **Внешние источники данных** — районы (журналы JSON Lines) и IDS
   Suricata (алерты).
2. **Пользователи SOC** — аналитик, старший аналитик, администратор SOC
   (работают через Dashboards и API).
3. **Единый вход Паспортного стола** — внешний IdP, через который
   аутентифицируются пользователи SOC.
4. **Шина Транспорта** — получает `city.grid.alarm.raised.v1`, публикует
   `city.soc.incident.opened.v1`.
5. **Collector (Fluent Bit)** — принимает журналы и алерты, пишет в
   OpenSearch и в append-only архив.
6. **API (Python)** — ведёт инциденты и статус источников в PostgreSQL.
7. **OpenSearch + Dashboards** — хранилище журналов и интерфейс аналитика.
8. **PostgreSQL и append-only архив** — хранилища состояния инцидентов и
   «холодных» журналов (объединены, так как оба являются data store
   с разными свойствами целостности).

## 2. Угрозы по STRIDE для каждого элемента

В таблице для каждого элемента перечислены только применимые классы
STRIDE. Угрозы сформулированы максимально конкретно для данного сервиса.

## 3. Три самые опасные угрозы

### 1. Подмена тегов и path traversal в Fluent Bit (S/T)

**Почему опасна:** Collector — единственная точка входа для всех журналов
районов и алертов Suricata. Если злоумышленник может подменить тег и
внедрить записи под доверенным тегом района (или перезаписать файлы через
path traversal), он получает возможность **скрывать свои действия** и
**фабриковать события** от имени доверенного источника. Для SOC это
означает потерю доверия ко всем данным мониторинга: аналитик не сможет
отличить реальный инцидент от подброшенного, а злоумышленник — «замести
следы» атаки. Эта угроза напрямую бьёт по целостности и неотказуемости
всей системы.

### 2. SQL-инъекция и повышение привилегий в API на Python

**Почему опасна:** API — единственный компонент, который **изменяет
состояние инцидентов и статуса источников** в PostgreSQL. SQL-инъекция
(или mass assignment ролей) позволяет не просто прочитать данные, а
**изменить статус инцидента** (закрыть реальный инцидент) или **повысить
привилегии** до администратора SOC. В сочетании с доступом к Dashboards
это даёт злоумышленнику возможность не только скрыть атаку, но и
управлять действиями аналитиков. Для SOC-сервиса компрометация API — это
компрометация процесса реагирования.

### 3. XSS / утечка через OpenSearch Dashboards (T/I)

**Почему опасна:** Dashboards — интерфейс, через который аналитики
**видят все журналы**. XSS через сохранённый объект (CVE-2026-77811)
позволяет злоумышленнику выполнить скрипт в браузере аналитика и
**украсть его сессию**, получив доступ к журналам, которые ему не
положены. Даже без XSS недостаточная проверка прав может привести к
утечке приватных ресурсов (CVE-2024-39900). В сервисе, который собирает
журналы со всех районов, утечка через Dashboards означает раскрытие
чувствительных данных города и потерю контроля над тем, кто и какие
события видит.

## 4. Что осталось за рамками из-за недостатка информации

- **Конкретная реализация единого входа** (SAML/OIDC, наличие MFA,
  политика сессий) не раскрыта — меры для IdP даны как базовые
  рекомендации.
- **Политика на шине Транспорта** (схемы сообщений, аутентификация
  издателей, ACL на топики) не детализирована — нельзя утверждать, что
  перечисленные меры уже действуют.
- **Конфигурация Шлюза** (WAF, rate limiting, терминирование TLS) не
  описана — часть мер по DoS и перехвату трафика может уже быть
  реализована на этом уровне.
